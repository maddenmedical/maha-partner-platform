# Security Review Results — Just Partner Portal (maha-app)
Reviewed before republish to a public `*.pplx.app` URL. Aug 14, 2026.

## Security Review Results

### BLOCK (must fix before publishing)

- **Real production admin credentials hardcoded in source** — `server/seed.ts:38` (`elisabeth.madden.medical@gmail.com` / `MahaAdmin2026!`) and `server/seed.ts:56` (`tina@maha.si` / `MahaTina2026!`). Confirmed these are **live, currently-active accounts** in the production database (`data.db`), not placeholder demo data — a real admin with a real personal Gmail address. Anyone who can read the published source (which will ship alongside the app) gets a working admin login and password in plaintext, plus it's printed to console via `console.log(..., "password:", adminPasswordPlain)`.
  **FIXED**: Edited `server/seed.ts` so both real-admin passwords are now required via environment variables (`ADMIN_SEED_PASSWORD`, `TINA_SEED_PASSWORD`) with no hardcoded fallback — the script now throws if they're not set, rather than silently seeding a known password. Demo/test accounts (`partner.demo@…`, `student.demo@…`) were left as-is since they are intentionally fake test fixtures, not real users.
  **Still needs a human decision**: Because `MahaAdmin2026!` and `MahaTina2026!` have already been exposed in source history, **rotate both admin passwords in the live database** (change password via the admin UI, or a one-off script) regardless of the code fix, since the fix only prevents *future* seed runs from reintroducing the known password — it does not invalidate a password that may already be known/leaked.

### WARN (inform user, let them decide)

- **Live secrets present in `.env`** — `/home/user/workspace/maha-app/.env` contains a **live Stripe restricted key** (`STRIPE_SECRET_KEY=rk_live_...`), a **Google OAuth client secret** (`GOCSPX-...`), a **Google OAuth refresh token**, a **Google service-account private key** (full RSA `BEGIN PRIVATE KEY` block), **VAPID private key**, and a **WordPress/LearnDash application password**. These are read only via `process.env` on the server — confirmed **not present** in any client-served asset (`grep` for `GOCSPX|BEGIN PRIVATE KEY|rk_live_|sk_live_` across `dist/public/assets/*.js` and all of `dist/` returned no matches). This is the expected, safe pattern for server-side secrets. However, `.env` is a plain file inside the workspace and is **not excluded via any `.pplxignore`-style mechanism** (none was found in this project) — if the publish process includes the full workspace/source tree rather than just `dist/`, this file would ship with the app. Suggested fix: confirm with the publish pipeline that `.env` is excluded from the published payload (same treatment as `node_modules`/`dist` in `.gitignore`), or accept this as a known risk since the server backend itself is not directly downloadable/browsable by end users of the deployed site (only `dist/public` is client-served).
- **Unauthenticated legacy upload-serving route** — `/api/uploads/:filename` (`server/routes.ts:115`) has no auth check and serves any file in `uploads/` by filename. `path.basename()` is applied, which blocks path traversal, and the one file currently present uses an unguessable UUID name, but this is a leftover pre-Drive-migration endpoint that could serve a partner's uploaded document to anyone who obtains/guesses the filename, with no ownership check. Suggested fix: add `requireAuth` + an ownership/role check consistent with `/api/files/:driveFileId`'s category-based authorization, or remove the route if no legacy records still reference local paths.
- **Real admin password also present in e2e test specs** — `e2e/drive-files.spec.ts:3`, `e2e/drive-oauth.spec.ts:8`, `e2e/v4-features.spec.ts:3`, `e2e/v6-education.spec.ts:3` all hardcode `MahaAdmin2026!` for test login. These files are not included in the `dist/` build artifact that is actually served, but they are present in the source tree. Suggested fix: after rotating the admin password (see BLOCK item), move test credentials to an env-var-driven test fixture instead of a literal string, and update these specs to match the new password.
- **High-severity transitive dependency vulnerabilities (no direct exploit path found)** — `npm audit` reports 2 high-severity issues: `brace-expansion` (DoS via unbounded expansion, [GHSA-mh99-v99m-4gvg](https://github.com/advisories/GHSA-mh99-v99m-4gvg) / [GHSA-rgw5-rvv9-x895](https://github.com/advisories/GHSA-rgw5-rvv9-x895)) pulled in transitively via `googleapis → googleapis-common → gaxios → rimraf → glob → minimatch`, and `nanoid` <3.3.18 ([GHSA-2v37-7h3g-55p8](https://github.com/advisories/GHSA-2v37-7h3g-55p8)) pulled in via `postcss` (a build-time dependency, not part of the running server). Neither sits on a path where attacker-controlled request input reaches the vulnerable code at runtime; both are fixable via `npm audit fix`. Suggested fix: run `npm audit fix` (or bump `postcss`/`googleapis` transitively) as routine maintenance, not urgent for this publish. 1 moderate finding was also present and ignored per the ≤10 threshold rule.

### PASS

- **SQL injection**: All DB lookups reviewed (`getUserByApprovalToken`, `getUploadedFileByDriveId`, session/user lookups) use Drizzle ORM's parameterized `eq()` query builder — no raw string concatenation found.
- **Path traversal**: Confirmed `driveFileId`-based lookups go through Google Drive's API (not filesystem paths); the one filesystem-path route (`/api/uploads/:filename`) uses `path.basename()` to strip traversal sequences.
- **Admin approval token routes** (`/api/admin/registration-action`, `/api/admin/registration-document` in `server/routes.ts`): Token is `crypto.randomBytes(24).toString("hex")` — 192 bits of entropy, cryptographically random, not sequential/predictable. Tokens are single-use (cleared via `setUserApprovalToken(id, null)` after a decision is made on the approve/decline route), and document access requires the same valid, still-active token. No way found to approve/decline or fetch a document for an arbitrary user without possessing their specific unguessed token.
- **Authenticated file-serving proxy** (`/api/files/:driveFileId`): Gated by `requireAuth` plus category-specific authorization (registration docs restricted to admins; referral/homework restricted to the owning user or admin; product files open to any signed-in user) — confirmed no cross-user document enumeration path.
- **XSS / dangerous-sink patterns**: Only one `dangerouslySetInnerHTML` use found (`client/src/components/ui/chart.tsx`), and it renders only developer-supplied chart theme/color config (standard shadcn/ui boilerplate) — not user-controlled input. No `eval`, `new Function`, or `document.write` usage found in the codebase.
- **Open CORS**: No `cors()`/wildcard `Access-Control-Allow-Origin` configuration found anywhere in the codebase — app relies on same-origin defaults, so no open-CORS mutation risk.
- **Critical dependency vulnerabilities**: Zero critical-severity findings in `npm audit` (0 critical, 2 high — both transitive/build-time, addressed above as WARN).
- **Client bundle secret leakage**: Verified no server secrets (Stripe key, Google service-account key, OAuth client secret) appear anywhere in the compiled client JS (`dist/public/assets/*.js`) or the rest of `dist/`.
